## 1. 已验证的基线

- 文件大小 7,897 字节；文件头为 `RSE1:`。
- 使用当前编辑器内置的 `h()` 解密成功，明文 5,882 字节、47 条非空记录、18 种记录类型。
- 在内存中执行 `h(G(plain)) === plain`，结果为 `true`。这只证明编解码一致，不能证明任意修改都符合游戏规则。
- 原始文件 SHA-256：`1f32274fee617b981c9f6f396f783b8fe7b600799fd1b3444d666814c4d60a72`。
- 现有天赋序列化器 `W(plain); e()` 会将术士的未知天赋 `demonic_familiar:5` 移至该行末尾；本样例仅发现这一处顺序差异，ID 和等级保留。无修改导出并非明文逐字一致。

最重要的结论：印记存在独立的职业记录；成就没有直接保存点数余额；地图难度的准确字段和枚举不能从单一样例确定。

## 3. 用户关心的三类配置

### 3.1 地图难度：先确定编码，地图通关不等于难度

样例的 `pick` 为以下结构（名字已隐去）：

```text
pick|8|5|1|sm|<name>|0,0,0,0,0|1
```

按包含 `pick` 的 `split('|')` 数组计数：

| 索引 | 值 | 本次可确定的含义 |
| --- | --- | --- |
| 0 | `pick` | 记录类型 |
| 1 | `8` | 当前出战职业，法师 |
| 2 | `5` | 与法师 `hero` 第一个数据字段相同；具体含义待核实 |
| 3 | `1` | 与法师 `hero` 第二个数据字段相同；具体含义待核实 |
| 4 | `sm` | 当前 `pick` 中的地图 ID，血色修道院 |
| 5 | 已隐去 | 角色名字 |
| 6 | `0,0,0,0,0` | 与法师 `hero` 五元组一致；各分量含义待核实 |
| 7 | `1` | 尚未核实的尾部字段，可作为难度调查候选，不能据此认定 |

同一份存档还存在：

```text
open|8|av
beat|8|elwynn,duskwood,wsg,ungoro,ab,feralas,arena,sm
```

`pick` 地图为 `sm`，`open` 为 `av`，两者本来就不一致。不能在用户修改难度或地图时自动把两者设成一样，也不能把 `beat` 中的地图数量当作难度。

实施前需要一组只切换游戏难度、不开始战斗的前后存档，比较 `pick` 全字段、`open` 以及新增记录。如果只变 `pick[7]`，再逐个难度导出，确认编号、范围及适用职业/地图。`1` 对应普通、困难、英雄或其他含义，目前均未证实。

验证后增加“出战设置”中的地图与难度选择器。难度使用已确认的枚举，遇到未知值显示原值并保留。地图进度面板继续处理 `beat`，避免混用。

### 3.2 成就点：不是成就条目数，也不是时间戳数量

样例包含 26 个 `ach` ID 和 24 个 `achat` 时间记录。其中 `talents:1`、`talents:9` 已在完成列表内，但没有对应时间记录。这是样例本来的状态，不能当作损坏自动修复或删除。

本文件中没有一个可直接确定为“成就点总额/余额”的独立字段，也没有保存每项成就的奖励点数。

需要补齐两个游戏定义表：

1. 成就定义：ID、名称、奖励点数、条件及关联解锁。
2. 永久强化定义：ID、每级效果、等级上限、每级费用，以及消费的是不是成就点。

如果游戏规则确认成就点由完成成就计算、并可消费于永久强化，则可按规则计算：

```text
已获得点数 = 所有已完成成就奖励点数之和
已消耗点数 = 各永久强化逐级费用之和（仅当确认共用该货币）
可用点数   = 已获得点数 - 已消耗点数
```

这只是需要验证的实现模型，不能用 `26`、`24`、强化等级之和或 `glow=1894` 代替实际点数。若成就目录不完整，应明确显示“无法完整计算”，不能默认为 0 点。

建议先做成就列表和点数预览，再做完成/撤销及永久强化等级编辑。编辑 `ach` 时按实际游戏规则处理 `achat`；已有缺失时间保持，新增时间采用明确策略，不能所有成就批量伪造同一时间。撤销成就前要检查是否导致点数不足或关联解锁不一致。

### 3.3 印记：职业记录和统计记录分开

样例存在两个相同的数：

```text
marks|8|445
stat|kills=107053,gold=98809,guardians=347,bosses=91,runs=44,wins=12,caches=274,marks=445
```

可以确认 `marks` 记录以职业 ID 为键，样例只存在法师 `8` 的记录。它是“印记数量”编辑的首要字段。`stat.marks` 属于统计记录，但仅凭两个值相同，还不能证明它们是同一余额或必须同步；它可能是累计统计，需要消费前后的存档验证。

建议界面增加“当前职业印记”非负整数输入；独立展示 `stat.marks`。通过一笔已知价格的游戏消费，确认哪些值扣减、是否同时修改其他记录，然后确定写入关系。不要默认将 `stat.marks` 设成当前职业余额，也不要对所有职业套用同一个数。

其他职业没有 `marks` 行，不应直接解释为“不支持印记”。初版可以只编辑已有记录；在游戏创建该职业第一笔印记的存档验证后，再支持新增缺失行。具体数值上限也需要依据游戏使用的数值类型确认。

## 4. 其他缺口与样例约束

- **统计页**：本例击杀 107053、金币统计 98809、守卫 347、Boss 91、局数 44、胜利 12、宝箱 274、印记统计 445。`stat.gold` 不应直接包装成可消费金币余额；是否参与成就计算需查规则。
- **永久强化**：`banish:1,companion:1,instinct_gold:1,keen:1,leash:3,opening:1,paws:3,rerolls:1`。现有页面只提供实验性重置次数恢复，本样例缺少 `resets`，并不提供这些强化的等级编辑。
- **实际装备与外观**：拥有某件装备不等于已经穿上它。`equip` 槽位包含 `15`、`17`，`look` 包含 `18` 和目录外 ID；不能使用当前收藏目录的 0–9 槽位直接覆盖它们。
- **职业外观档案**：`pick` 中的部分字段和法师 `hero` 一致，修改外观可能需要同步两处。但不能据此认定每次修改职业、名字或难度都需要重写所有 `hero`。
- **图鉴与宠物**：分别有 `seen` 和 `pets`，可新增收藏页；未知 ID 或状态必须保留。
- **保底与 `glow`**：先提供原始值只读检查；只有消费/获取前后对照或游戏源码能确认名称及更新关系。
- **天赋目录滞后**：样例的 `demonic_familiar:5` 未被内置天赋目录识别，当前通过 `unknown` 保留。增加新属性时也应沿用保留未知数据的原则。

## 5. 在现有代码中如何落地

### 5.1 解析层：保留原始记录，增加局部草稿

当前核心脚本高度混淆，不适合继续直接堆叠字段逻辑。沿用已有扩展脚本和 `window.__AS_EDITOR_BRIDGE`，抽出可读的记录解析/变更模块。

- 保存原始行、顺序、换行格式和尾部字段，按 `kind + classId` 或单例记录定位。
- 使用独立草稿表示用户明确修改的字段；无修改的记录尽量逐字保留。
- `ach` 为集合；`achat`、`stat`、`seen` 是 `=` 键值；`perk`、`pity` 是 `:` 键值；不能让一个简单分隔器覆盖所有结构。
- `legendary:fireball=4`、`class:mage=时间值` 的 ID 本身有冒号，不能以冒号直接切成两半。
- 重复记录不能无声覆盖；未知 ID、空字段和未来新增尾字段必须可透传。

### 5.2 界面层：按账号与职业组织

- 出战设置：当前职业、名字、地图、确认后的难度。
- 当前职业：印记、装备穿戴、外观、天赋构筑。
- 账号：成就与点数预览、永久强化、宠物、图鉴。
- 统计/高级检查：`stat`、未确认的 `pity`、`glow`、未知记录。

导航、修改数量、撤销恢复、原始备份、底部统一导出应涵盖新增草稿。切换职业时分别缓存，不得串改。

### 5.3 导出层：必须同步升级三处保护

现有 `mergeAndVerify()` 只合并装备、构筑同步、地图通关和可选 `resets`。仅增加表单不会让新值进入最终文件。

1. 在 `mergeAndVerify()` 中应用新增草稿，按确切记录和字段验证写入值。
2. `verifyAccountProgressPreserved()` 当前保护 `seen|ach|achat|stat|hero|equip|look|perk|pets`。扩展为“未修改记录保持一致；已修改记录匹配草稿”的验证，不能删除整段保护。
3. `withoutEdits()` 当前只豁免 `items`、`beat/unlock/spec` 和可选 `resets`。应基于实际变更记录验证差异，不能简单把所有新类型整体豁免。

之后补充 bridge 的 `snapshot()`，让新增字段进入 `areas`、`fingerprint`、修改预览与恢复逻辑。

最终仍执行 `h(G(result)) === result`。此外必须检查不相关记录保留及游戏关系约束；加密回环通过不等于游戏会接受或持久化该修改。

## 6. 推荐实施顺序与验证材料

| 顺序 | 功能 | 实施条件与下一步 |
| --- | --- | --- |
| 1 | 记录审计、统计及高级原值展示 | 结构已确认，可先实现只读展示 |
| 2 | 已有职业印记编辑 | 字段明确；消费前后对照确认与 `stat.marks` 的关系 |
| 3 | 地图与难度设置 | 补一组仅切换难度的存档，逐项确认字段与枚举 |
| 4 | 成就点预览、永久强化编辑 | 补齐游戏版本对应的成就奖励和强化费用表 |
| 5 | 装备穿戴、构筑切换、图鉴、宠物 | 分别确认槽位、目录和依赖关系 |
| 6 | 外观、保底、`glow` | 单独采样验证后开放写入 |

最小采样建议：

- 同一角色、同一地图，只切换难度后导出。
- 一次固定价格印记消费前后导出，避免随机购买混入保底变化。
- 不完成新成就，仅购买一级永久强化前后导出，并记录游戏界面点数。
- 完成一项已知奖励成就前后导出，确认点数来源与时间记录。
- 若要开放 `glow`，再采集一次对应资源获取/消费；未找到对应行为前保持原值。

这些样本应来自同一游戏版本。对每个新编辑项至少验证“只改该项”“切换职业”“重新导入编辑器”“导入游戏后立即检查”和“完成一局后再次检查”。

## 7. 可复用的只读分析工具

已添加 `tools/analyze-save.cjs`，不依赖第三方包，使用当前编辑器的编解码逻辑并验证回环。它只向标准输出写报告，不写存档。输出包含角色名字及进度，分享前自行删去个人信息。

```powershell
node tools/analyze-save.cjs "C:/path/to/before.sav"
node tools/analyze-save.cjs "C:/path/to/before.sav" "C:/path/to/after.sav"
```

第二种用法同时输出两份结构化摘要及按记录类型分组的原始差异。它报告结构差异，不会自动给未知字段命名，也不会声称游戏已接受修改。
